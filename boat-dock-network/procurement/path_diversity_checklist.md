# Path Diversity Verification — Two Head-Ends, Two Routes

> How we *prove* (not assume) that our two middle-mile on-ramps are truly independent
> (doc 17 §6 step 3). "Redundant" only counts if a single backhoe, a single POP, or a
> single upstream can't take us fully offline. This is the acceptance test we run on
> provider quotes before we sign.

## 1. The four layers that must all be diverse
A pair of links can share a hidden single point of failure at any of these. Check each:

1. **Physical route (conduit / right-of-way):** the two fibers must not ride the same
   conduit, the same aerial pole line, or the same bridge/crossing. Ask each provider for
   **KMZ/GIS route maps**; overlay both and look for any shared segment. The lake itself is
   a natural diversity aid — POP A on the NW shore, POP B reached from the east/south.
2. **Structure / entrance:** the two circuits must enter our head-ends (and the carrier
   POPs) through **separate building entrances / vaults / risers**, not one shared MPOE.
3. **Optical/L1 shared fate:** on lit waves, confirm the two waves don't ride the **same
   DWDM line system or the same amplifier huts**. "Two waves on one fiber pair" is *not*
   diversity. Prefer different line systems, ideally different providers.
4. **Upstream / L3 (IP transit):** the two transit feeds must reach the internet via
   **different upstream ASNs and different peering/transit mixes**, so one upstream's
   outage or route leak doesn't blackhole both. Multi-home our own ASN across both.

## 2. Acceptance test (run per candidate pair)
| Check | Evidence we require | Pass criteria |
|-------|--------------------|---------------|
| Route separation | KMZ/PDF route maps for A and B | **0 shared conduit/pole/bridge** segments |
| Min. separation | maps / provider attestation | routes materially apart (no common chokepoint); document any forced-common points (e.g., one bridge) as accepted risk |
| Entrance diversity | site drawings / survey | separate entrances & vaults at both head-ends and carrier POPs |
| Optical diversity | provider L1 design | different line systems / amp sites, or dark fiber on separate pairs |
| Upstream diversity | transit AS-path info | different upstream ASNs on A vs B |
| Failover proof | our BGP config + test | pull path A → all traffic rides B within convergence target, and vice-versa |

## 3. How we test it for real (turn-up)
- **BGP design:** advertise our prefixes out both paths; prefer-A / prefer-B tuning with
  full failover. Each on-ramp provisioned to carry **100% of load** (1+1, per
  `transit_sizing.py`).
- **Failover drill:** at turn-up and quarterly, **shut path A** and confirm the lake stays
  up on B (watch NOC latency/loss), then restore and repeat for B. Log MTTR.
- **Route-leak / RPKI hygiene:** publish ROAs for our prefixes; ask both upstreams to
  filter by our AS + prefixes.

## 4. If perfect diversity isn't available
- A single unavoidable common point (one lake bridge, one shared aggregation POP) →
  document it as **accepted residual risk**, and mitigate (e.g., a licensed-microwave
  lake-crossing hop as an L1 backup — ties to the OSP design, doc 03/04).
- Two products from **one** provider is the weakest form — only accept it if they prove
  separate line systems *and* separate entrances, and treat provider-level outage as the
  residual risk. **Prefer two different providers.**
